이 코드는 **모델을 돌리는 코드가 아니라, 노드와 노드 사이의 "택배 구간(SPI 링크)" 하나가 제대로 작동하는지 확인하는 시험용 코드**입니다.

## 코드가 하는 일

보드 두 대가 실제 시스템의 이웃한 두 노드를 흉내 냅니다.

```
[보드 A: 송신]  ── 1) 헤더(8B): "토큰 N개, 길이 L" ──►  [보드 B: 수신]
                 ◄── READY: "그 길이로 받을 준비 끝" ──
                 ── 2) 페이로드(N×512×2B) ──────────►
                                                       3) 내용이 맞는지 검사
```

- **송신(A)**: 토큰 수를 1, 2, 4, 8, 12, 16, 24로 돌려 가며 헤더와 페이로드를 보냅니다. 페이로드는 실제 모델 값이 아니라 **규칙으로 만든 가짜 데이터**이고, 크기만 실제 활성값(토큰 수 × 512 × 2바이트)과 같습니다.
- **수신(B)**: 헤더를 먼저 받아 길이를 읽고, **그 길이에 맞춰 수신 DMA를 다시 장전한 뒤** READY를 올려서 페이로드를 받습니다. 그리고 데이터가 규칙대로인지(`mismatch`), 길이가 맞는지(`lenOk`), 순번이 이어지는지(`seqGap`), 헤더 CRC가 맞는지(`badHdr`)를 검사해 출력합니다.

## 실제 시스템과의 대응

| 시험 코드 | 실제 시스템에서 |
| --- | --- |
| 송신 보드 A | 앞 노드 (Pico 1, S3 #1, #2, #3 중 하나) |
| 수신 보드 B | 뒤 노드 (S3 #1 ~ #4 중 하나) |
| 가짜 페이로드 | 레이어 연산 결과(활성값) |
| 토큰 수 1~24 | 문장 길이에 따른 가변 패킷 |
| 헤더 + READY 2단계 | 계획했던 "문장마다 패킷 크기를 재설정하는 방식" |

## 이 로그가 증명한 것

1. **배선과 핀맵이 맞습니다.** 정해둔 GPIO 연결(4→12, 5→11, 6→10, 15→16, GND)대로 두 보드가 실제로 통신합니다.
2. **가변 길이 패킷이 하드웨어에서 동작합니다.** 패딩 없이 1KB부터 24KB까지 문장 길이에 따라 크기가 바뀌어도, 수신 측이 헤더를 읽고 DMA를 재장전하는 방식이 실제로 통했습니다. 앞서 논의한 "패킷 사전 조정" 아이디어가 구현 가능하다는 첫 번째 증거입니다.
3. **READY 핸드셰이크가 데이터 유실을 막습니다.** 수신 준비가 되기 전에 보내지 않으니 유실이 없습니다(`seqGap=0`).
4. **DMA 경로가 데이터를 깨뜨리지 않습니다.** 24KB까지 바이트 단위로 정확히 일치합니다.

## 이 로그가 증명하지 못한 것

- **속도 한계**: 지금은 낮은 클럭에서 맞는지만 본 것입니다. 얼마나 빠르게 올릴 수 있는지는 클럭을 올려 봐야 압니다.
- **장시간 안정성과 오류 복구**: 짧은 실행이었고, 헤더가 깨졌을 때 다시 맞추는 기능은 아직 없습니다.
- **중간 노드 동작**: 실제 체인의 중간 노드는 받으면서 동시에 보내야 하는데, 이 코드는 한쪽은 보내기만 하고 다른 쪽은 받기만 합니다.
- **연산과 통신의 겹침**: 연산 중에 다음 데이터를 받는 동작은 아직 시험하지 않았습니다.
- **Pico와의 호환**: Pico 1이 마스터, S3가 슬레이브인 구간은 별도로 시험해야 합니다.
- **모델 자체**: BERT 연산은 전혀 포함되어 있지 않습니다.

## 의미

시스템의 모든 구간(Pico 1 → S3 #1 → #2 → #3 → #4)이 **같은 방식으로 데이터를 주고받기 때문에, 이 구간 하나를 먼저 확실하게 검증해 두는 것**이 핵심입니다. 이후 단계에서는 이 구간을 믿고 쌓아 올립니다. 통신이 불안정한 상태로 연산 코드를 얹으면, 결과가 틀렸을 때 연산 문제인지 통신 문제인지 가려내기 어려워집니다.

비유하면 택배 트럭이 정해진 길을 오가는지, 짐을 흘리지 않는지를 **빈 상자로 먼저 시험한 것**입니다. 다음 단계는 중간 노드(받으면서 보내는 노드)를 만들어 체인으로 이어 보는 것입니다.
